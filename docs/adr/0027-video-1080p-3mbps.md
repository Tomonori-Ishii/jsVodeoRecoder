# ADR-0027: 映像は 1920×1080、約 3Mbps にする（ADR-0016 を置き換える）

- **Status**: Accepted（実機での録画と ffprobe の確認は未実施）
- **Date**: 2026-11-22

## Context

Issue #1 で、録画の画面を 1280×720 から 1920×1080 に変更する要望があった。
ADR-0016 の 1Mbps は 720p 向けに決めた値で、1080p に変えると 1 ピクセルあたりのビット数が約半分になる。

模擬計測（libx264、スクロールするテキスト、10 秒。SSIM の dB。大きいほど良い）:

| 条件 | SSIM (dB) |
|---|---|
| 720p・1.0Mbps | 40.4 |
| 720p・1.5Mbps | 44.4 |
| 1080p・1.0Mbps | 31.4 |
| 1080p・2.0Mbps | 39.5 |
| 1080p・3.4Mbps | 46.3 |

1080p で 1.0Mbps のままでは、画質が 720p より悪くなる。同等の画質には約 3Mbps が必要になる。
資料閲覧で動きが小さい場合、2 時間の映像は、上限いっぱいでも 3Mbps で約 2.7GB になる（最悪ケース）。

## Decision

- 録画の解像度は **1920×1080** にする（縮小は 16:9 を保ち、余白は黒にする）。
- 映像のビットレートの上限は **3Mbps** にする（`VIDEO_BITRATE` = 3000000）。
- H.264 のレベルは **4.0**（`avc1.4d4028`）にする。レベル 3.1 は 1080p の最大フレームサイズを満たさない。mp4 の avcC も同じ値にする。
- 空き容量の録画開始の下限は **6GB**（仮）にする。2 時間の中間データ（約 2.6GB）と mp4（約 2.6GB）が同時に必要になるため（ADR-0022 の 3GB から変更）。
- フレームレート 10fps、H.264、mp4、音声（Opus 128kbps）は変えない。

## Consequences

- 2 時間の録画: 中間データと mp4 が、それぞれ約 2.8GB になる（ピークは約 5.6GB）。
- 1 フレームの処理量（描画、画素の読み出し、比較、符号化）は、720p の約 2.25 倍になる。CPU 負荷は増える（ADR-0019）。10fps を保てない場合は、フレームレートが下がる。
- 1080p・3Mbps の画質は、模擬計測で 720p・1.5Mbps と同程度とした。実機の OpenH264 での確認が必要。
- レベル 4.0 を OpenH264 が受け付けない場合は、録画を開始できない（`NO_H264`）。実機で確認する。
- ビットレートを上げたため、ADR-0022 の数値と、設計書の容量見積もりを更新した。

## Alternatives

- 1080p・1.0Mbps: 画質が 720p より悪くなるため採らない。
- 720p・1.0Mbps のまま: Issue #1 の目的を満たさないため採らない。
- 1080p・2.2Mbps: 容量は約 2.0GB だが、模擬計測で 720p・1.5Mbps に届かないため採らない。
